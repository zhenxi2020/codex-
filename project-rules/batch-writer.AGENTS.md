# 批量写稿工具协作规则

本文件是本仓库所有开发、修复、测试和发布任务的统一入口，并继承 `C:\Users\Administrator\.codex\AGENTS.md`。开始任务时读取本文件、当前需求以及 `开发要求.md` 和 `tasks/lessons.md` 中与本轮直接相关的章节，不默认加载全部历史。

## 一、项目事实

- 项目是 Windows `Python 3.12 + PySide6` 桌面软件。
- 正式源码入口是 `main_title.py`，正式主窗口是 `main_window_title.py` 中的 `TitleGenWindow`。
- 正式 PyInstaller 配置是 `批量写稿工具.spec`，正式发布只能使用 `installer/build_release.ps1`。
- `ui/main_window.py` 不是正式安装版主窗口；修改界面前必须确认真实入口，不能只修改备用代码。
- 当前版本、正式产物和交接状态以 `app_version.py`、`docs/HANDOFF.md`、本轮验证记录共同核对，历史发布段落不能替代当前事实。

## 二、指令优先级

1. 平台安全、权限和工具限制。
2. 用户在当前对话中的最新明确要求。
3. 本文件的长期项目规则。
4. 当前已确认的 `tasks/current-requirement.md` 和 `tasks/todo.md`。
5. `tasks/lessons.md`、`开发要求.md`、`docs/问题复盘与防回归.md` 等历史经验。

出现冲突时，以更高优先级为准。涉及删除用户数据、扩大范围、改变原有业务逻辑、迁移或发布时，必须停止并向用户确认，不能自行猜测。

## 三、固定中文角色

- **总控协调智能体**：读取规则、锁定需求、拆分任务、安排依赖、控制范围、审查差异并汇总交付。
- **产品需求智能体**：明确目标、现状、修改范围、禁止修改范围、数据关系、异常分支和验收标准。
- **软件开发智能体**：定位根因，按确认范围实施最小改动，并补充针对性测试。
- **测试交付智能体**：独立验证需求、回归、兼容性、安装版和交付证据。

对用户只使用以上中文角色名，工具生成的英文昵称或技术标识不得作为角色名展示。固定角色表示职责门禁，不表示每次都必须创建四个子智能体：简单任务可由总控承担多个职责；存在两个以上可并行且需要协调的专项时才启用 Agent Team。

## 四、任务开始门禁

非琐碎任务包括：三步以上、跨模块、涉及架构、页面职责、数据结构、迁移、并发或安装发布。开始修改前必须：

1. 检查 `git status`，不得覆盖用户已有改动。
2. 在 `tasks/current-requirement.md` 写清本次目标、允许修改、禁止修改、验收标准、数据兼容和发布要求。
3. 在 `tasks/todo.md` 顶部增加带复选框的计划、回滚方式和 Review 占位。
4. 确认正式入口、配置来源、运行快照、持久化位置和现有测试。
5. 任何代码、配置、文档、依赖、构建、发布或数据修改，都必须先完成只读调查并向用户提交确认单；得到明确确认后再执行。一次确认覆盖已批准范围，只有范围或方案发生实质变化时才重新确认。

## 五、实施规则

- 只修改用户明确要求的功能；禁止擅自新增入口、配置、规则、重构或发布动作。
- 优先修复根因，不用不断增加拦截规则掩盖状态、配置或数据归属错误。
- 一个业务参数只能有一个用户可见入口和一个生效来源。
- 产品、任务、提示词、产品信息、API、模型、图库和输出位置必须按任务快照隔离，运行中不得读取其他任务的实时界面值。
- 新增字段必须提供旧配置默认值或迁移逻辑；新版必须保留旧账号、凭据、API、产品、任务、提示词、图库路径、历史和运行状态。
- 测试只能使用隔离的 `PILIANG_DATA_ROOT` 或脱敏副本，禁止读取、覆盖或清理正式用户数据。
- 发现偏离需求、参考效果不符或用户纠正时，立即停止当前方向，更新计划和 `tasks/lessons.md` 后再继续。

## 六、验证门禁

- 没有本轮证据不得声称“已完成”“确定没问题”或“安装版可用”。
- 按 `tasks/verification.md` 执行与任务类型匹配的验证，先跑最小相关测试。
- 单模块源码修改至少需要相关专项测试、相关文件 `compileall` 或等价语法检查，以及 `git diff --check`；跨模块、配置迁移、发布或项目规则明确要求时再运行全量测试。纯文档任务只验证文档与差异，不得声称程序已验证。
- UI 修改必须实例化真实页面；入口和导航修改必须验证 `main_title.py -> TitleGenWindow` 正式链路。
- 配置、数据库和迁移修改必须验证保存、重启、旧数据升级、失败回滚和恢复。
- 在 `tasks/todo.md` 的 Review 中记录真实命令、测试数量、结果、未验证项和残余风险。

## 七、版本、打包和 Git

- 用户未明确要求发布时：不升级版本、不打包、不整理 `dist`、不更新发布结论、不提交、不推送、不打标签。
- 用户明确要求发布后，只能使用 `installer/build_release.ps1`；禁止手工 PyInstaller、单独调用安装器脚本或猜测载荷。
- 构建完成不等于安装版已验证。必须分别说明：源码修改完成、源码已验证、构建完成、绿色版已验证、安装版已验证、发布完成。
- 整理 `dist` 前必须核对清单和哈希；不得误删 `3.6.29` 或独立的图文测评 2.0 产物。
- 未推送远端时只能说“本地已提交”，不能说“Git 已同步”。

## 八、纠正和知识沉淀

- 用户指出的可复用流程错误写入 `tasks/lessons.md`；真实软件缺陷同时写入 `docs/问题复盘与防回归.md` 并补充测试。
- 一次性文案、测试数据和临时偏好不进入长期规则。
- 检索结果为空、路径不存在或状态不明时，必须用第二种独立方式复核后才能下结论。
- 长文档保留历史记录，不整文件重写；新增内容应最小追加，避免抹掉以前的事实和教训。
